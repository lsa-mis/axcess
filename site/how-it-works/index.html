How it works

From a web address to a verified fix

Axcess follows the way an accessibility expert already works. Here is each step in plain language, followed by what the checks actually look at and how sure each one is.

The workflow

Six steps, one scan

  1. Choose the site

    Pick a public website, or choose Login or 2FA website for a site that needs a sign-in. For a protected site, Axcess opens a visible browser window and you sign in yourself, with your password, passkey, or one-time code. Axcess never asks for any of them.

    Only scan sites you are authorized to test.

  2. Set the scope

    Decide which part of the site to cover: a single section such as /admissions/ or the whole site. Set a page limit, how deep to follow links, and how gently to crawl. A live preview shows what the scope means before you start.

  3. Watch the scan

    You see the current page, how many pages were discovered, loaded, and tested, which checks ran and which were skipped, and an estimated finish time. Live updates never steal your keyboard focus or jump the page.

  4. Read the report

    One table lists every issue and answers four questions: What is the issue? Why does it matter? What is the expected fix? Where exactly is it? Repeated occurrences are grouped so a single cause is fixed once.

  5. Open the evidence

    Follow any issue to the page, the element, the snippet, the rule, or the screenshot that produced it. Everything is stored with the scan, so a claim can be checked months later.

  6. Export and verify

    Record your decisions, export the workbook or report, assign the work, and rescan when fixes land. The comparison shows what is new, resolved, and still open.

Under the hood, in plain words

What each check looks at

A scan runs several independent checks. Each result keeps the name of the check that produced it, so two methods are never blended into one unexplained verdict.

Rule engine

The widely used axe-core engine inspects each rendered page for machine-testable problems: missing image descriptions, broken headings, form fields without names, low contrast, and more.

Deterministic

Second opinion

Optionally, Siteimprove's independent Alfa engine takes its own look. Where the two engines agree or disagree is visible, which helps you judge how solid a result is.

Deterministic

Keyboard check

Axcess presses Tab and Shift+Tab through each page looking for places where keyboard users get stuck. It is deliberately cautious: ordinary focus loops and dialogs are not reported as traps.

Browser-observed

Zoom and reflow check

Each page is squeezed to a phone-width view, zoomed to about 200%, and given wider text spacing to see whether anything is cut off or overlaps.

Browser-observed

Focus check

Finds keyboard focus hidden behind sticky headers or banners, and tab orders that were forced out of sequence.

Browser-observed

Click through states

Axcess can open menus, tabs, and dialogs and re-run the rule engine on what appears. It never clicks links, never presses anything named sign out, delete, or unsubscribe, and stops after a bounded number of clicks per page.

Deterministic

Image text check

Text hidden inside pictures is invisible to screen readers and cannot be resized. Built-in text recognition finds it; an optional local vision model judges whether the image is really just text.

AI-assisted lead

Visual and motion check

Measures video and audio that autoplay without controls, records scrolling text, and, with a local vision model, compares the visual reading order to the order a screen reader would hear.

Mixed

Meaning check

With a local language model, asks judgement questions a rule engine cannot: does this link make sense out of context? Does this heading describe its section? Is this form field explained well enough?

AI-assisted lead

Every AI-assisted check is optional and runs on a local model you install yourself. Without one, the browser-only checks still run in full. See exactly which WCAG criteria each check covers.

Evidence before verdicts

How sure is each result?

Not all findings are equally certain, and Axcess never pretends they are. Results travel in three separate lanes, and a lead can never silently become a confirmed barrier.

Likely barrier

Deterministic rule failures

A rule engine measured something on the rendered page and it failed. High confidence, though a person still verifies the fix.

Review lead

Browser-observed behaviour

Axcess operated the page and saw something suspicious, such as focus that would not leave an element. The evidence is real; the interpretation needs an expert.

Needs confirmation

AI-assisted suggestions

A local model made a judgement call. These are strong leads, clearly labelled, and always confirmed or rejected by a person before they count.

Decisions are recorded, not just made. Each issue group can be accepted, rejected as a false positive, marked remediated, or kept open as an accepted risk, with a written rationale and a history of who decided what and when.

Modern websites

Works with apps, not just pages

Many sites today are applications built with React, Vue, Angular, or similar frameworks. A traditional crawler sees an empty shell. Axcess renders every page in a real browser first.

Routes are discovered by following real links

Axcess follows links it can see on rendered pages, including app-style routes, and stays inside the scope you set. It does not guess private addresses or read application code.

States are counted separately from pages

When Axcess opens a menu or dialog and tests what appears, it reports that as a DOM state alongside the page count, not folded into it. A page count alone would undersell an app; counting states as pages would oversell the crawl.

Interaction is bounded and safe

Links are never clicked by the probe. Controls named sign out, delete, remove, unsubscribe, or deactivate are refused. Each page is capped at 40 clicks and two levels of newly revealed controls.

Some things still need a person

Hover-only content, gestures, operating-system menus, embedded third-party widgets, and states without a visible change on the page are outside what the probe can see. The report says so.

Follow-up

Rescan and compare

A fix is only real when a later scan shows it. Run the same scope again and Axcess lines the two reports up.

New

Barriers seen now that were not in the earlier scan.

Resolved

Barriers from the earlier scan that are no longer observed under the same scope and checks.

Still open

Barriers present in both scans, so the work is not finished yet.

"Not found this time" is not automatically "fixed". Axcess compares the same scope and methods, and a confirmed fix should still pass a retest or a human check.

What Axcess is not. Axcess produces accessibility evidence for a qualified person to review. Automated and AI-assisted results do not prove WCAG conformance, legal compliance, or the accessibility of an entire website, and they do not replace testing with people who use assistive technology.
